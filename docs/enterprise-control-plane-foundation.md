# Enterprise control-plane foundation (not an enabled product feature)

This repository contains **unmounted** organization read, member deactivation, administrator demotion and session-kill APIs, a server-owned single-host directory, an OIDC authorization-code client with S256 PKCE, and a separately unmounted HTTP callback router. The shipped desktop's Account settings intentionally reports that enterprise administration is not configured. `EnterpriseAdminDashboard` is exercised with loopback-only mock fixtures; it is not shown to employees or connected to a production identity provider. The unmounted, administrator-only activity view shows at most 20 tenant-scoped events; a separate authenticated JSON download returns the bounded full tenant audit snapshot and records an export event. Neither is a deployed audit export, retention or SIEM implementation.

## Shared durable directory backend (not selected by the desktop)

`PostgresDirectoryStore` offers a bounded shared database backend for multiple server instances. It uses a single PostgreSQL row with `SELECT ... FOR UPDATE` inside the same-client transaction as permission checking, session revocation, mutation and audit append. There is no fallback to a workstation-local directory on database failure. Bootstrap is an explicit operator action; ordinary reads never create the table or a tenant. A database operator applies the `ENTERPRISE_DIRECTORY_SCHEMA` DDL from `server/enterprise/postgresDirectoryStore.ts` using a separate migration role, then grants only SELECT/INSERT/UPDATE on that table to the application role. Provision the TLS CA, host, database, user and password through the deployment secret channel (never source control); `createEnterprisePostgresPool` requires a pinned CA and hostname-validated TLS, rejects URI configuration, and bounds connection/lock/statement waits. Do not use a privileged service-role key in a renderer or browser.

This is a bounded **8 MB aggregate state** pilot seam, not a scalable tenant-partitioned database, unlimited audit log, HA guarantee, backup or retention implementation. Snapshot backup/restore, recovery drills, operational audit export, credential rotation, access-policy mapping to execution and proven multi-host deployment are still required. Alongside deterministic protocol mocks, `bash scripts/test-enterprise-postgres-local.sh` runs actual PostgreSQL 14 on loopback with a disposable one-day local CA, a restricted throwaway role, two independent TLS pools, HTTP cross-tenant/role/revocation tests and an outage-negative test. The same fixture exercises generated-key OIDC callback/replay with multi-host database state and a separate directly TLS-served loopback callback: pinned CA rejection, host-only Secure cookies, origin/tenant/CSRF denials and durable session logout. The direct HTTPS test found that Bun's encrypted server socket does not inherit Node's TLSSocket prototype; origin verification now checks the actual socket's encryption flag without trusting forwarded headers. These synthetic checks do **not** prove reverse-proxy trust, real domain/issuer ownership, Electron cookie custody or installed Windows behavior. The script stops its isolated server and removes its private ephemeral keys on exit; it does not connect to a default cluster or external service. It requires a locally installed PostgreSQL 14 distribution and a writable private `/workspace/private` test workspace; it is an operator-run test, not CI's external dependency or a deployment fixture. `mountEnterpriseAdminRoutes` is a **default-off composition seam** for a separately reviewed HTTPS server and requires a pinned organization and issuer plus a server-owned verifier. Its plaintext loopback exception requires explicit test mode. Neither the OIDC login nor admin router is mounted by the desktop HTTP sidecar, and no employee-facing SSO/admin capability is enabled: a configured host must separately prove issuer/audience/domain ownership, callback and proxy/TLS/cookie custody, administrator bootstrap, backup/rollback and operational audit retention before enabling them. [node-postgres transaction rules](https://node-postgres.com/features/transactions) require the same client throughout a transaction; its [SSL documentation](https://node-postgres.com/features/ssl) warns that URI SSL parameters can override an explicit CA.

`TenantPostgresDirectoryStore` is an **unselected** next-step backend with one operator-created row per pinned organization and the same row-locked authorization/revocation/audit transaction. Its own `ENTERPRISE_TENANT_DIRECTORY_SCHEMA` must be applied separately; no shipped request chooses or creates a row. The disposable TLS fixture proves two rows and two independent pools cannot cross-read through their pinned store instances and tenant-scoped HTTP mounts; a foreign snapshot fails validation, and a missing or blank row cannot silently grant authority. This is **application-level** tenant isolation only: the test role still has table-wide permissions, each row has an 8 MB cap, and there is no production migration from the earlier singleton, PostgreSQL RLS, per-tenant database credential, HA/backup drill or append-only external audit retention. Do not select this backend for a deployment until those boundaries are reviewed and exercised.

The separate, **unselected** `'rls'` mode requires the operator to apply `ENTERPRISE_RLS_TENANT_DIRECTORY_SCHEMA`, enable and FORCE row-level security, pre-provision exactly one row bound to an independent `NOINHERIT NOBYPASSRLS` login role, and grant that role SELECT plus UPDATE of `content` only—not INSERT, DELETE, table ownership or BYPASSRLS. No browser request or application bootstrap can create an absent RLS row. A separate RLS audit table receives new validated events in the **same transaction** as the tenant snapshot; its application role has SELECT and INSERT only, with no UPDATE or DELETE. Locked mutations and preliminary session reads compare **ordered ledger content**, not only row count, with the tenant snapshot; the application role cannot rewrite earlier ledger entries. The disposable independent-role TLS fixture executes the exact three exported operator DDL strings rather than copied schemas, then verifies direct SQL row isolation, cross-host revocation, operator-simulated missing and same-count rewritten events, and HTTP 503 when the ledger diverges. A third synthetic role commits one workspace, a session revocation, a verified synthetic DNS domain claim and a domain-bound session; an immediate local database restart demonstrates that scoped directory state, ordered audit, revocation and claim-gated session survive reconnect. The fixture takes an operator `pg_dump` snapshot, restores it into a second database in that **same disposable cluster**, and rechecks revocation, workspace, ledger, the domain claim and bound session, plus cross-role denial through fresh restricted TLS connections. This is **not** an independent backup, off-host restore, HA or production crash-recovery certification. This detects drift, not a cryptographic guarantee against an operator who can rewrite both copies or backups. It is **local database enforcement proof**, not production isolation or an operational append-only retention guarantee: role lifecycle, sealed per-tenant credentials, migrations from either pilot format, backup/restore, retention, operational RLS policy review and authorized deployment remain required.

That RLS schema also defines an operator-owned, globally unique domain-claim registry. Each tenant role needs `SELECT`, column-limited `INSERT(domain, organization_id, database_role, issuer)`, and **only** `UPDATE(database_role)` on the registry; no table-wide `UPDATE`, `DELETE`, or updates to domain, organization or issuer are allowed. The RLS `WITH CHECK` constrains `database_role` to `current_user`, so that narrow column grant permits row-locking reads without transferring a claim; the per-operation boundary guard rejects expanded grants or missing column grants. An operator must provision and independently review these privileges and retain the ability to release a claim. Creating a challenge reserves nothing globally and never consults another tenant's claim, so it cannot block a name or reveal who holds it. The claim row is inserted only when DNS verification first succeeds, in the same transaction as the tenant proof and audit, including across independent server hosts. A foreign claim is hidden by RLS but the unique constraint denies the duplicate, rolls back the tentative verification and records a denial in the requesting tenant's audit ledger. A verified lease is not reported if its registry entry disappears or cannot be read; a database outage returns an error, not a positive status. A new challenge keeps an existing lease; only a completed DNS answer for the tenant's own live challenge that lacks the expected value clears it (not a lookup error, missing or expired challenge, or denial), and a successful verification extends it. Domain-proof routes accept a live, unrevoked domain-bound administrator session for its own bound domain while the tenant still holds the claim even if the 24-hour lease has lapsed, so renewal cannot deadlock on the lease it renews; every other action still requires a current lease. Claims are **not automatically released** on lease lapse: operator-reviewed release/transfer is necessary. A tenant administrator can hold challenges for up to the bounded directory quota of 32 names; the registry does not prove legal entitlement, prevent a compromised database role from reserving arbitrary names, establish a production domain/issuer or authorize SSO activation. The disposable fixture exercises cross-tenant collision, direct-SQL RLS/permission denial, registry read outage and operator transfer. Migration of existing domain proofs and tenant credentials must be reviewed before selecting this backend.

RLS-mode operations also query PostgreSQL's role, table-security and privilege metadata on each read and locked write. An operator mistake that grants `BYPASSRLS`, leaves a role inheritable, disables forced RLS on the three tables, gives the application a table-owner role or grants forbidden insert/update/delete privileges denies requests instead of trusting application-level tenant checks; the disposable fixture changes one role to `BYPASSRLS` and verifies both the store and HTTP boundary return unavailable until the operator restores it. This is a defensive guard, **not** a proof against a privileged operator changing grants concurrently with a request, modifying policies, replacing the schema or forging backups; deployment still requires independent privilege and recovery review.

All store queries and operator DDL pin the `public` schema rather than relying on a connection's `search_path`; the TLS fixture creates a same-named temporary RLS table on an application connection and proves scoped reads and writes still use the authorized row. This does not replace database privilege hardening or an audit of every operational SQL role.

The unmounted OIDC client now fetches [OpenID Connect Discovery configuration](https://openid.net/specs/openid-connect-discovery-1_0.html) at the issuer-derived well-known path before initiating login and again after consuming browser state, before code exchange. A successful login-start check is reused for at most 60 seconds per integration instance (failures are never reused); the pre-exchange check is never cached. Login-start state is stored by state digest, bounded per transport-level client network (IPv6 by /64; forwarded headers are not trusted) and per tenant, and a full bound evicts the oldest attempt of that client or of the busiest client rather than refusing a start; a callback whose state is unknown, expired or wrongly bound is rejected by a read without a directory write. It fails closed unless the reported issuer and authorization/token/JWKS endpoints exactly match operator-pinned configuration and the metadata advertises code flow, public-client token exchange, S256 and a permitted signing algorithm. Metadata outage or drift denies login; it does not silently trust an email domain or swap endpoints. The disposable local fixture also exercises actual CA-verified HTTPS requests to a generated-key IdP for discovery, code exchange and JWKS, with a separate HTTPS callback and two independent TLS PostgreSQL pools; metadata drift consumes a browser attempt before token exchange. This does not attest a real organization issuer, domain ownership, production CA/host configuration or installed desktop cookie custody.

The unmounted production OIDC integration and HTTP router now require an exact lowercase pinned `accountDomain`. Login start and the signed-ID-token callback both require a current organization-and-issuer-matched domain proof **and** a database-wide claim check; a file pilot or tenant-only store cannot pass this activation gate. The authorization request includes `email`; the callback requires a signed `email_verified: true` and an exact email domain before the server-owned directory may issue a session for an already-provisioned subject. Session issuance rechecks the proof in the locked tenant snapshot and holds a database row lock on the operator-owned domain claim **through the session-and-audit commit**; a concurrent release either waits for that commit or is seen as a missing claim. Domain-bound sessions retain the pinned domain, and subsequent server-side session verification fails closed if its proof or claim disappears, including after operator release or registry outage. Every authenticated directory transaction reselects the caller's persisted binding, locks the current claim, and checks policy in the same tenant transaction before audit or mutation. The disposable RLS/TLS HTTP fixture checks a release injected between callback precheck and final session transaction (denial without a session cookie), subsequent use of a previously valid session after release (403; registry outage returns 503), and release after HTTP verification but before member deactivation (503; member unchanged). The CA-pinned HTTPS IdP and secure host-only callback fixtures now use separate throwaway RLS tenant roles, DNS proof and signed verified synthetic email; no unbound HTTPS test bypass is retained. Synthetic tests deny absent/false verified-email claims, foreign or suffix-lookalike domains, registry withdrawal between start and callback, and missing proof. This does not prove account entitlement, the issuer's email-verification policy or a production domain; even this stricter client and router remain **unmounted** and must not be exposed before real issuer/domain, deployment and independent security acceptance.

## What the foundation does

- An operator-only bootstrap pins each organization's issuer and provisions its first administrator. There is no anonymous or browser-accessible bootstrap endpoint.
- A configured OIDC client creates one-time state, nonce, PKCE verifier and browser binding; exchanges a code only at its pinned token endpoint; verifies a signed ID token against the pinned JWKS URI, issuer, audience, nonce, authorized party, time and allowed algorithms; then checks server-owned membership. The OIDC ID token is **not** accepted as a Workstation API bearer token.
- The unmounted callback router pins the application origin and callback path, rejects unexpected query parameters and forwarded-host substitution, and uses host-only `HttpOnly`, `SameSite=Lax`, `Secure` cookies outside explicit loopback-only test mode. It never puts the opaque session in a URL or renderer storage. Production TLS and reverse-proxy trust topology still require review.
- A separate unmounted same-origin browser API resolves the cookie server-side, checks current session and tenant/role through the locked directory, and fails closed on revocation and audit failure. Its non-test HTTPS composition requires an exact pinned account domain and OIDC callback mapping for the same tenant, issuer, domain and application origin; it snapshots those pins before mounting. It uses the directory's persisted domain-bound session verifier, not a caller-supplied verifier that could admit an unbound operator session. The later directory transaction locks and rechecks the claim; a fixture HTTPS test rejects both an unbound session with a deliberately permissive injected verifier and a valid same-tenant/issuer session bound to a different verified domain, including after caller configuration mutation. The read-only dashboard does not accept a token prop or set an `Authorization` header. Its fixture tests are not deployed browser-session proof.
- A separately unmounted admin mutation API accepts only same-origin JSON with exact Origin, a non-simple CSRF header, a current HttpOnly session and the same tenant-bound administrator policy. It can deactivate an existing member, demote another active administrator while retaining at least one active administrator, revoke a member's sessions, or end every current session in its own organization (including the administrator's), never create or promote one. Demotion atomically revokes that administrator's existing sessions; they may sign in again as a member. The locked transaction records accepted changes and attributable denials; pre-authentication, invalid-origin and malformed requests are not a complete security audit ledger. The dashboard requires confirmation and authoritative refetch for member and role changes; organization-wide kill hides data and does not refetch on the revoked caller session. A failed change hides stale data.
- A separately unmounted, same-origin sign-out API revokes the caller's own opaque session and appends its audit event in the same locked transaction before clearing the HttpOnly cookie. The dashboard hides its directory while revocation is pending and reports an outage without falsely claiming sign-out. The separate organization-wide session action invalidates other current local organization sessions, but neither action invalidates upstream IdP sessions, credentials, endpoints or running environments; those lifecycle controls remain unimplemented.
- Session-kill leaves membership intact, so members can authenticate again until independently deactivated. A self-admin session uses sign-out; the organization-wide action includes its initiating administrator and clears that browser cookie after its locked audit commit. That transaction advances the tenant's login epoch and removes pending OIDC browser attempts; an attempt already consumed on another host must still match the new epoch at session creation after its code exchange, so an in-flight pre-kill login cannot reopen access. Fresh logins begun after the kill use the new epoch. This does not revoke upstream IdP sessions. Cross-tenant URL probes from an active, verified session are logged in **the actor's tenant only**, including read, export, mutation and logout paths. Forged or revoked identities cannot create attributed denial records. The unmounted audit export is bounded by the pilot's 8 MB state limit, records its own event, and lacks operational retention, SIEM delivery and recovery proof.
- The server creates a random opaque session; only its SHA-256 digest is retained. Directory reads check the current session, pinned issuer, organization and active admin membership in one locked operation and commit an audit event before returning data. Demoting a member revokes that member's sessions in the same write.
- Server-owned directory writes use restrictive filesystem permissions, an exclusive cross-process lock and atomic replace. A stale lock, failed audit write, corrupt state or missing identity fails closed. This is a bounded **single-host prototype**, not a distributed or hardened database, SIEM, SCIM server, execution policy engine or credential vault. Windows directory-flush durability remains unproven and needs retained-fleet validation.
- Persisted organization, membership, attempt, session and audit records are schema/tenant-checked before use or replacement. Explicit maintenance removes expired attempts and sessions without deleting audit events. Denied reads, cross-tenant probes and unprivileged members' denied mutations are collapsed into one event per actor, action, outcome and target kind in each fixed 10-minute window, with a count and first/last timestamps. A caller-chosen target is kept as a 16-hex-digit SHA-256 prefix only while all repeats share it; otherwise the event explicitly marks mixed targets and retains the kind without falsely attributing the count to the first target. The open window's counter is held in the tenant snapshot and appended as a single event (one append-only RLS ledger row) by the next such denial after the window closes. Successful mutations and administrator verification failures remain individually recorded. Ordinary writes stop 512 KB below the 8 MB cap; only allowed member deactivation, member or organization session revocation, self sign-out, administrator sign-in (attempt start/consume and an administrator session) and expiry compaction may use that reserve. Audit growth remains rate-bounded, not total-bounded; it still reaches the ordinary capacity limit over time. This is **not** a production retention or recovery design.
- An optional **unselected** `node:sqlite` backend exercises `BEGIN IMMEDIATE` transactions, WAL and synchronous writes with the same authorization logic. Local Node fixtures prove restart, rollback, tenant denial and corrupt-record rejection. Node's SQLite API is experimental; packaging compatibility, Windows crash recovery, backup/restore, migrations, audit retention/export and multi-host operation remain unverified. No desktop path selects this backend.
- An experimental, **unmounted and unselected** `rls-v2` store mode models a versioned tenant checkpoint and a bounded directory row with committed events only in the append-only RLS table. Its separate offline migration validates each legacy tenant against ordered canonical ledger text and aborts the whole transaction on a mismatch; a guarded operator-only script requires a private backup file and matching SHA-256, pinned TLS and a FORCE-RLS-bypassing role. The operator must separately verify that the backup can actually restore. The v2 mode checks an indexed tail plus tenant event count instead of hydrating the full ledger on every request; that count can still scan a growing index. Its store-level page primitive rechecks a domain-bound admin session, role, claim and stable upper cursor under a tenant row lock, records allowed/member-denied requests in the same transaction and reports still-open denial windows separately. A fresh export page closes up to 100 pending windows into the ledger before fixing the upper cursor; a continuation keeps that upper cursor stable, and another fresh pass is necessary while pending windows remain. A failed ledger insert rolls back both the close and request. A separate, **unmounted** HTTP page factory tests same-origin cookie, tenant, role, cursor, outage and revocation boundaries with a synthetic RLS store; the desktop and opt-in admin composition do not register it. The legacy unpaged activity/export API fails closed in v2. No complete audit download or browser client has been accepted; real PostgreSQL migration/TLS acceptance is missing. Do not select or enable it for production, call it F1 resolution, or infer audit retention/HA from synthetic tests.
- Unmounted domain discovery returns only an exact configured issuer/tenant hint, not membership or authorization. A SCIM-shaped projection cannot cross its pinned tenant or promote an IdP-supplied group to admin; there is no SCIM ingress or provisioning write. A server-owned default-deny policy seam protects existing directory read/member actions and categorically denies agent execution, tool invocation and SCIM provisioning. Those denials are not Workstation-wide policy enforcement.
- An independently opt-in workspace administration registry stores at most 32 bounded identifiers/names per organization in the same tenant transaction. The server, not a local filesystem path or renderer claim, enforces current session, role and tenant on listing, registering and deactivating entries, with scoped success/denial audit. Cross-tenant URL probes write only the actor's tenant ledger. The dashboard refetches authoritative inventory and hides it on a denied or unavailable mutation. These records do **not** govern local folders, agents, tools, connectors, memberships or execution; no deployed server selects the route, and workspace isolation is not a shipped claim.

The [OpenID Connect Core ID-token validation rules](https://openid.net/specs/openid-connect-core-1_0-18.html), [PKCE S256](https://www.rfc-editor.org/rfc/rfc7636.html) and [OAuth security best current practice](https://www.rfc-editor.org/rfc/rfc9700.html) are the standards references. `jose` is used for signed token/JWKS verification; no competitor code or assets were imported.

## Required before mounting or displaying SSO

1. Independently threat-model deployment authority, trusted HTTPS origin, exact callback URI, account-domain to organization mapping, pinned issuer/JWKS endpoints, redirect/cookie rules, client registration, state/browser binding and IdP metadata. The current local-loopback exception is a test-only constructor option, not a production setting.
2. Independently review and deploy the unmounted callback through an authorized TLS origin with exact account-domain mapping; validate browser binding, CSRF, login/logout, session expiry/revocation and concurrent browser/Electron lifecycle end to end. A local fixture is not proof of production cookie custody or reverse-proxy safety.
3. Replace the single-file directory with a reviewed durable transactional store and backup/restore, retention, migration and audit-export design. Define provisioning ownership, emergency suspension, SCIM group/user lifecycle and IdP-session invalidation. Do not equate a local filesystem workspace with an organization tenant.
4. Enforce policies across agent, tool, IPC, sidecar and execution paths, including direct-route bypass tests. Hold secrets server-side. Verify connector ACL inheritance and revocation before any knowledge-layer security claim.
5. Run an approved end-to-end local IdP deployment with a real callback/account-domain configuration and installed desktop revision, and review dashboard loading, denied, empty and populated states. Then publish and roll out through the ordinary protected release path.

There are no production domains, IdP credentials, paid services or SSO feature flags in this foundation. Tests use only generated local keys and temporary directories.

## Anonymous callback work boundary

An unknown or wrongly bound OIDC callback is a negative-only lookup, never an authentication decision. The experimental RLS tenant store now probes its bounded directory snapshot after checking the tenant database role and RLS boundary, without scanning the growing audit ledger. A matching candidate is **not** trusted on that read: consuming it still takes the tenant lock and validates the complete ledger checkpoint, browser binding, expiry and login epoch. A probe outage fails closed. This removes one history-dependent query from anonymous unknown-state callbacks but is not an ingress rate limiter, a multi-host load test, or permission to enable login.

## Audit-page size boundary

The experimental v2 page limits each returned ledger entry to 64 KiB at the SQL projection, so a 100-event page cannot hydrate unbounded historic text. Its writer rejects oversized new events atomically; the offline migration rejects oversized legacy or pending events rather than omitting them from export. An installation with such history needs an operator-reviewed preservation/migration solution, not truncation or an automatic retry. This is a per-request memory bound, not evidence of throughput, durable retention or safe production export.

## Expired-domain recovery boundary

The expired-lease renewal exception is **not complete account recovery**. It requires a still-live administrator session bound to that domain and its existing global claim. Once all bound administrator sessions expire or are revoked, a new domain-bound OIDC login is denied while proof is expired and the current browser flow cannot issue a new challenge. A synthetic negative test covers this lockout; an independently authorized operator recovery path and live cross-host acceptance are required before enterprise activation.

## Local browser acceptance (fixture only)

With the repository's existing dependencies installed, build the isolated view using `pnpm exec vite build --config tests/enterprise-admin/vite.config.ts`, then run `NODE_ENV=test pnpm exec tsx tests/enterprise-admin/server.ts`. The fixture binds **only** `127.0.0.1:39394`; visit `/fixture/login` to create a local generated administrator session and inspect the actual React dashboard at `/`. Confirm deactivation of the fixture member and verify that the active count changes, the row becomes inactive and audit count rises. The fixture has a second synthetic administrator: confirm their demotion, observe the admin count and row role refresh, and verify the initiating/last administrator has no demotion control. The fixture also explicitly mounts the workspace-registry route: register one synthetic workspace, confirm deactivation and observe the refreshed inactive entry, without inferring filesystem or agent access. Before login the dashboard must deny access. A focused browser-state test switches organization while a prior tenant's sign-out is in flight: a new tenant remount cannot display the old directory or accept its late notice. This is not a multi-organization cookie/session migration test. Unit fixtures in `server/enterprise/adminMutation.test.ts` cover CSRF, cross-tenant requests, member actors, last-admin protection, replay, session revocation, audit failure and parallel reads. This test server is not mounted by `server/server.ts` and is not a production login flow.

For a separate **synthetic visual-only** export fixture, run `pnpm exec vite --config scripts/fixtures/enterprise-audit.vite.config.ts --host 127.0.0.1 --port 55472` and visit `/scripts/fixtures/enterprise-audit-fixture.html`.
