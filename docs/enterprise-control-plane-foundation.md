# Enterprise control-plane foundation (not an enabled product feature)

This repository contains **unmounted** organization read, member deactivation and session-kill APIs, a server-owned single-host directory, an OIDC authorization-code client with S256 PKCE, and a separately unmounted HTTP callback router. The shipped desktop's Account settings intentionally reports that enterprise administration is not configured. `EnterpriseAdminDashboard` is exercised with loopback-only mock fixtures; it is not shown to employees or connected to a production identity provider. The unmounted, administrator-only activity view shows at most 20 tenant-scoped events; a separate authenticated JSON download returns the bounded full tenant audit snapshot and records an export event. Neither is a deployed audit export, retention or SIEM implementation.

## Shared durable directory backend (not selected by the desktop)

`PostgresDirectoryStore` offers a bounded shared database backend for multiple server instances. It uses a single PostgreSQL row with `SELECT ... FOR UPDATE` inside the same-client transaction as permission checking, session revocation, mutation and audit append. There is no fallback to a workstation-local directory on database failure. Bootstrap is an explicit operator action; ordinary reads never create the table or a tenant. A database operator applies the `ENTERPRISE_DIRECTORY_SCHEMA` DDL from `server/enterprise/postgresDirectoryStore.ts` using a separate migration role, then grants only SELECT/INSERT/UPDATE on that table to the application role. Provision the TLS CA, host, database, user and password through the deployment secret channel (never source control); `createEnterprisePostgresPool` requires a pinned CA and hostname-validated TLS, rejects URI configuration, and bounds connection/lock/statement waits. Do not use a privileged service-role key in a renderer or browser.

This is a bounded **8 MB aggregate state** pilot seam, not a scalable tenant-partitioned database, unlimited audit log, HA guarantee, backup or retention implementation. Snapshot backup/restore, recovery drills, operational audit export, credential rotation, access-policy mapping to execution and proven multi-host deployment are still required. Alongside deterministic protocol mocks, `bash scripts/test-enterprise-postgres-local.sh` runs actual PostgreSQL 14 on loopback with a disposable one-day local CA, a restricted throwaway role, two independent TLS pools, HTTP cross-tenant/role/revocation tests and an outage-negative test. The same fixture exercises generated-key OIDC callback/replay with multi-host database state and a separate directly TLS-served loopback callback: pinned CA rejection, host-only Secure cookies, origin/tenant/CSRF denials and durable session logout. The direct HTTPS test found that Bun's encrypted server socket does not inherit Node's TLSSocket prototype; origin verification now checks the actual socket's encryption flag without trusting forwarded headers. These synthetic checks do **not** prove reverse-proxy trust, real domain/issuer ownership, Electron cookie custody or installed Windows behavior. The script stops its isolated server and removes its private ephemeral keys on exit; it does not connect to a default cluster or external service. It requires a locally installed PostgreSQL 14 distribution and a writable private `/workspace/private` test workspace; it is an operator-run test, not CI's external dependency or a deployment fixture. `mountEnterpriseAdminRoutes` is a **default-off composition seam** for a separately reviewed HTTPS server and requires a pinned organization and issuer plus a server-owned verifier. Its plaintext loopback exception requires explicit test mode. Neither the OIDC login nor admin router is mounted by the desktop HTTP sidecar, and no employee-facing SSO/admin capability is enabled: a configured host must separately prove issuer/audience/domain ownership, callback and proxy/TLS/cookie custody, administrator bootstrap, backup/rollback and operational audit retention before enabling them. [node-postgres transaction rules](https://node-postgres.com/features/transactions) require the same client throughout a transaction; its [SSL documentation](https://node-postgres.com/features/ssl) warns that URI SSL parameters can override an explicit CA.

`TenantPostgresDirectoryStore` is an **unselected** next-step backend with one operator-created row per pinned organization and the same row-locked authorization/revocation/audit transaction. Its own `ENTERPRISE_TENANT_DIRECTORY_SCHEMA` must be applied separately; no shipped request chooses or creates a row. The disposable TLS fixture proves two rows and two independent pools cannot cross-read through their pinned store instances and tenant-scoped HTTP mounts; a foreign snapshot fails validation, and a missing or blank row cannot silently grant authority. This is **application-level** tenant isolation only: the test role still has table-wide permissions, each row has an 8 MB cap, and there is no production migration from the earlier singleton, PostgreSQL RLS, per-tenant database credential, HA/backup drill or append-only external audit retention. Do not select this backend for a deployment until those boundaries are reviewed and exercised.

The separate, **unselected** `'rls'` mode requires the operator to apply `ENTERPRISE_RLS_TENANT_DIRECTORY_SCHEMA`, enable and FORCE row-level security, pre-provision exactly one row bound to an independent `NOINHERIT NOBYPASSRLS` login role, and grant that role SELECT plus UPDATE of `content` only—not INSERT, DELETE, table ownership or BYPASSRLS. No browser request or application bootstrap can create an absent RLS row. A separate RLS audit table receives new validated events in the **same transaction** as the tenant snapshot; its application role has SELECT and INSERT only, with no UPDATE or DELETE. Locked mutations and preliminary session reads compare **ordered ledger content**, not only row count, with the tenant snapshot; the application role cannot rewrite earlier ledger entries. A disposable two-role TLS fixture verifies direct SQL row isolation, cross-host revocation, operator-simulated missing and same-count rewritten events, and HTTP 503 when the ledger diverges. This detects drift, not a cryptographic guarantee against an operator who can rewrite both copies or backups. It is **local database enforcement proof**, not production isolation or an operational append-only retention guarantee: role lifecycle, sealed per-tenant credentials, migrations from either pilot format, backup/restore, retention, operational RLS policy review and authorized deployment remain required.

All store queries and operator DDL pin the `public` schema rather than relying on a connection's `search_path`; the TLS fixture creates a same-named temporary RLS table on an application connection and proves scoped reads and writes still use the authorized row. This does not replace database privilege hardening or an audit of every operational SQL role.

The unmounted OIDC client now fetches [OpenID Connect Discovery configuration](https://openid.net/specs/openid-connect-discovery-1_0.html) at the issuer-derived well-known path before initiating login and again after consuming browser state, before code exchange. It fails closed unless the reported issuer and authorization/token/JWKS endpoints exactly match operator-pinned configuration and the metadata advertises code flow, public-client token exchange, S256 and a permitted signing algorithm. Metadata outage or drift denies login; it does not silently trust an email domain or swap endpoints. The disposable local fixture also exercises actual CA-verified HTTPS requests to a generated-key IdP for discovery, code exchange and JWKS, with a separate HTTPS callback and two independent TLS PostgreSQL pools; metadata drift consumes a browser attempt before token exchange. This does not attest a real organization issuer, domain ownership, production CA/host configuration or installed desktop cookie custody.

## What the foundation does

- An operator-only bootstrap pins each organization's issuer and provisions its first administrator. There is no anonymous or browser-accessible bootstrap endpoint.
- A configured OIDC client creates one-time state, nonce, PKCE verifier and browser binding; exchanges a code only at its pinned token endpoint; verifies a signed ID token against the pinned JWKS URI, issuer, audience, nonce, authorized party, time and allowed algorithms; then checks server-owned membership. The OIDC ID token is **not** accepted as a Workstation API bearer token.
- The unmounted callback router pins the application origin and callback path, rejects unexpected query parameters and forwarded-host substitution, and uses host-only `HttpOnly`, `SameSite=Lax`, `Secure` cookies outside explicit loopback-only test mode. It never puts the opaque session in a URL or renderer storage. Production TLS and reverse-proxy trust topology still require review.
- A separate unmounted same-origin browser API resolves the cookie server-side, checks current session and tenant/role through the locked directory, and fails closed on revocation and audit failure. The read-only dashboard does not accept a token prop or set an `Authorization` header. Its fixture tests are not deployed browser-session proof.
- A separately unmounted admin mutation API accepts only same-origin JSON with exact Origin, a non-simple CSRF header, a current HttpOnly session and the same tenant-bound administrator policy. It can deactivate an existing member, revoke that member's sessions, or end every current session in its own organization (including the administrator's), never create or promote one. The locked transaction records accepted changes and attributable denials; pre-authentication, invalid-origin and malformed requests are not a complete security audit ledger. The dashboard requires confirmation and authoritative refetch for member changes; organization-wide kill hides data and does not refetch on the revoked caller session. A failed change hides stale data.
- A separately unmounted, same-origin sign-out API revokes the caller's own opaque session and appends its audit event in the same locked transaction before clearing the HttpOnly cookie. The dashboard hides its directory while revocation is pending and reports an outage without falsely claiming sign-out. The separate organization-wide session action invalidates other current local organization sessions, but neither action invalidates upstream IdP sessions, credentials, endpoints or running environments; those lifecycle controls remain unimplemented.
- Session-kill leaves membership intact, so members can authenticate again until independently deactivated. A self-admin session uses sign-out; the organization-wide action includes its initiating administrator and clears that browser cookie after its locked audit commit. Cross-tenant URL probes from an active, verified session are logged in **the actor's tenant only**, including read, export, mutation and logout paths. Forged or revoked identities cannot create attributed denial records. The unmounted audit export is bounded by the pilot's 8 MB state limit, records its own event, and lacks operational retention, SIEM delivery and recovery proof.
- The server creates a random opaque session; only its SHA-256 digest is retained. Directory reads check the current session, pinned issuer, organization and active admin membership in one locked operation and commit an audit event before returning data. Demoting a member revokes that member's sessions in the same write.
- Server-owned directory writes use restrictive filesystem permissions, an exclusive cross-process lock and atomic replace. A stale lock, failed audit write, corrupt state or missing identity fails closed. This is a bounded **single-host prototype**, not a distributed or hardened database, SIEM, SCIM server, execution policy engine or credential vault. Windows directory-flush durability remains unproven and needs retained-fleet validation.
- Persisted organization, membership, attempt, session and audit records are schema/tenant-checked before use or replacement. Explicit maintenance removes expired attempts and sessions without deleting audit events. Audit growth still reaches the pilot's capacity limit despite the download seam; this remains **not** a production retention or recovery design.
- An optional **unselected** `node:sqlite` backend exercises `BEGIN IMMEDIATE` transactions, WAL and synchronous writes with the same authorization logic. Local Node fixtures prove restart, rollback, tenant denial and corrupt-record rejection. Node's SQLite API is experimental; packaging compatibility, Windows crash recovery, backup/restore, migrations, audit retention/export and multi-host operation remain unverified. No desktop path selects this backend.
- Unmounted domain discovery returns only an exact configured issuer/tenant hint, not membership or authorization. A SCIM-shaped projection cannot cross its pinned tenant or promote an IdP-supplied group to admin; there is no SCIM ingress or provisioning write. A server-owned default-deny policy seam protects existing directory read/member actions and categorically denies agent execution, tool invocation and SCIM provisioning. Those denials are not Workstation-wide policy enforcement.

The [OpenID Connect Core ID-token validation rules](https://openid.net/specs/openid-connect-core-1_0-18.html), [PKCE S256](https://www.rfc-editor.org/rfc/rfc7636.html) and [OAuth security best current practice](https://www.rfc-editor.org/rfc/rfc9700.html) are the standards references. `jose` is used for signed token/JWKS verification; no competitor code or assets were imported.

## Required before mounting or displaying SSO

1. Independently threat-model deployment authority, trusted HTTPS origin, exact callback URI, account-domain to organization mapping, pinned issuer/JWKS endpoints, redirect/cookie rules, client registration, state/browser binding and IdP metadata. The current local-loopback exception is a test-only constructor option, not a production setting.
2. Independently review and deploy the unmounted callback through an authorized TLS origin with exact account-domain mapping; validate browser binding, CSRF, login/logout, session expiry/revocation and concurrent browser/Electron lifecycle end to end. A local fixture is not proof of production cookie custody or reverse-proxy safety.
3. Replace the single-file directory with a reviewed durable transactional store and backup/restore, retention, migration and audit-export design. Define provisioning ownership, emergency suspension, SCIM group/user lifecycle and IdP-session invalidation. Do not equate a local filesystem workspace with an organization tenant.
4. Enforce policies across agent, tool, IPC, sidecar and execution paths, including direct-route bypass tests. Hold secrets server-side. Verify connector ACL inheritance and revocation before any knowledge-layer security claim.
5. Run an approved end-to-end local IdP deployment with a real callback/account-domain configuration and installed desktop revision, and review dashboard loading, denied, empty and populated states. Then publish and roll out through the ordinary protected release path.

There are no production domains, IdP credentials, paid services or SSO feature flags in this foundation. Tests use only generated local keys and temporary directories.

## Local browser acceptance (fixture only)

With the repository's existing dependencies installed, build the isolated view using `pnpm exec vite build --config tests/enterprise-admin/vite.config.ts`, then run `NODE_ENV=test pnpm exec tsx tests/enterprise-admin/server.ts`. The fixture binds **only** `127.0.0.1:39394`; visit `/fixture/login` to create a local generated administrator session and inspect the actual React dashboard at `/`. Confirm deactivation of the fixture member and verify that the active count changes, the row becomes inactive and audit count rises. Before login the dashboard must deny access. Unit fixtures in `server/enterprise/adminMutation.test.ts` cover CSRF, cross-tenant requests, member actors, last-admin protection, replay, session revocation, audit failure and parallel reads. This test server is not mounted by `server/server.ts` and is not a production login flow.

For a separate **synthetic visual-only** export fixture, run `pnpm exec vite --config scripts/fixtures/enterprise-audit.vite.config.ts --host 127.0.0.1 --port 55472` and visit `/scripts/fixtures/enterprise-audit-fixture.html`. Check desktop and narrow-screen layout, download the synthetic JSON, verify only `synthetic-org` events, and toggle the denied view. This page intercepts requests locally and is **not** the real PostgreSQL/IdP HTTP acceptance above. The server-side export and cross-tenant/outage negatives run through the disposable TLS PostgreSQL fixture; neither fixture enables the shipped admin route.
