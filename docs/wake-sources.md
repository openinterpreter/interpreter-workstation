# Thread wake sources

Automations are inputs to an ordinary persistent thread, not a separate agent or conversation type. Open the thread and expand **Automations** above its composer to add, change, or cancel a schedule or a trusted host command. The dot indicates configured sources; each row displays its next run, current state, and a bounded error. Idle conversations are allowed. An incoming input steers an active turn or starts a turn on **the same thread** when idle; it does not wait in a foreground tool call.

## Schedule

Set an ISO-8601 first time and a message. A repeat interval, if present, must be at least one minute. At most one occurrence per source awaits admission. After confirmed native transcript admission, the next recurrence is calculated from the current time, not the original due time. A restart coalesces missed occurrences into one input; it never catches up an unbounded backlog. Cancelling stops future runs and removes inputs not yet offered. An already offered or admitted turn is not interrupted.

For a daily **civil clock** instead of a fixed elapsed interval, provide `dailyAt` (`HH:mm`) and an IANA `timeZone` such as `America/Los_Angeles`, without `at` or `everyMs`. The next eligible local calendar day is recalculated after admission; the clock time remains stable across daylight-saving changes. On a spring-forward day when that wall time does not exist, that day is skipped. On a fall-back day when a wall time occurs twice, only the first occurrence is used. Restarts coalesce missed days to at most one input and resume on the next eligible local day after admission.

For an existing errored recurring schedule with a reviewed **held** occurrence, the calling thread can use `inspect-recovery` with its exact source ID to obtain a source-and-events revision. `recover-future` requires that revision and the exact held event ID. It retains the held occurrence and starts only a future recurrence: the next civil clock time for `dailyAt`/`timeZone`, or the current time plus `everyMs` for a valid fixed-interval `at`/`everyMs` source. An unresolved pending or offered occurrence, mismatched revision, paused source, malformed schedule, or unknown custody refuses without changing any source or event. This operation does not admit or replay the held occurrence. Inspect and decide its custody separately before invoking a future-only recovery; do not create a replacement source.

From the conversation itself, `interpreter-app tools builtin-interpreter interpreter_wake_schedule --json '{"action":"list"}'` lists schedules. Use `{"action":"upsert","message":"...","at":"2026-10-01T09:00:00Z"}` to create one, add `everyMs` for recurrence, and supply an existing `id` to change or cancel (`{"action":"cancel","id":"..."}`). This supported tool is scoped to its calling thread; it cannot schedule another conversation.
For daily local time use `{"action":"upsert","message":"...","dailyAt":"07:00","timeZone":"America/Los_Angeles"}` instead of `at`/`everyMs`.

For an easy-to-find configuration view in a headless thread, call the same tool with `{"action":"config"}`. It returns that thread's schedule rows and the absolute path of the **single** private `wake-sources.json` state file. The file also contains native admission receipts and command sources: do not hand-edit, replace, or watch it as a second scheduler. To edit a schedule declaratively, keep a small JSON request file with `action`, optional stable `id`, `message`, `dailyAt`, and `timeZone`, and pass it to `interpreter-app tools builtin-interpreter interpreter_wake_schedule --json-file /absolute/path/to/request.json` from **that thread**. `upsert` validates the clock and IANA zone before changing any state, then atomically replaces the same mode-0600 state file (including an fsync of the containing directory); `cancel` retains admitted dedup receipts. `list` and `config` do not write. The request file is an input to this tool, not a second live configuration registry. Restrict its permissions if its message contains private instructions, and do not execute schedule instructions received from untrusted text.

## Trusted command

Configure an absolute executable and JSON array of arguments. This executes on the Workstation host under its own operating-system permissions, without a shell. **Only add a command you trust**; never take an executable or arguments from untrusted inbound text. A command has a 200-second timeout and a 3,088,384-byte stdout limit (room for 16 maximum-length messages even when every character is `\uXXXX`-escaped); stderr is not placed in the transcript. Exit 0 must write UTF-8 newline-delimited JSON to stdout, one object per line (a final newline is optional). Either a single line means there is no input:

```json
{"status":"waiting"}
```

or one to 16 event lines, in the order they should reach the thread, optionally followed by one final `{"status":"more"}` line when the source has more ready input than it emitted:

```json
{"id":"source-stable-event-id-1","message":"An ordinary user input"}
{"id":"source-stable-event-id-2","message":"A second input"}
{"status":"more"}
```

A single event line is the one-event case of this format. Each `id` must be stable for redelivery of the same upstream event (letters, digits, `_`, `-`, at most 160) and appear once per run; each `message` must contain a non-whitespace character and be at most 32,000 characters. An event line carries exactly `id` and `message`, and a status line exactly `status`. Every line is validated before anything is ingested: a malformed line, any other key, an invalid or repeated ID, a blank or over-long message, more than 16 events, `waiting` together with events, `more` anywhere but last after at least one event, an unknown `status`, or output over the stdout limit rejects the **whole** run as a source error and ingests nothing. Events of one run are taken into custody together, in order, with one durable write; an ID the source already handed over keeps its stored input, whatever wording the source now prints for it, so re-emitting a batch is harmless.

The source does not run again while any of its own inputs awaits admission; this is its back-pressure. After `waiting` it polls again after at least 30 seconds. After a run that produced new input (with or without `more`), it runs again **immediately** once the last of those inputs is confirmed in native thread history, so a burst drains without a 30-second gap; the next run reports `waiting` when it is empty. If every ID of a run already had a receipt, it waits the 30-second minimum instead, whatever the run reported. "Awaits admission" includes an input the runtime has already accepted but whose receipt is not yet in history (see [Accepted and admitted](#accepted-and-admitted)). The dispatcher offers a thread's inputs one after another, in order, and does not wait for one input's receipt before offering the next: a burst is steered into the running turn in one pass (see [Accepted and admitted](#accepted-and-admitted)). A steer refused because the turn ended in the meantime returns the input to pending without backoff and without a source error, and that turn is remembered as ended. A follow-up pass then starts the now-idle thread, unless an earlier input of the thread is still bound to that ended turn (accepted, receipt not yet seen): the refused input then waits until that earlier input's receipt appears, or until the two-pass proof under [Unconfirmed offers](#unconfirmed-offers) returns it to pending (at least a minute after it was offered, plus 15 seconds), and it is offered first. When history still reports the refused turn as active, the next steer goes to that turn again; if it is refused again, the input stays pending with a visible source error and is retried after one minute, and the following refusal counts as a first one again, so while history keeps reporting that turn the input alternates between an immediate retry and a one-minute wait. A refusal of a turn that history did not report as active (the turn of an earlier accepted input) always returns the input to pending without backoff or error, and that turn is not steered again. Nonzero exit, invalid output, other native admission failures, and authentication/usage failures become visible source errors without rapid respawn or model/account fallback. Re-save a corrected source to retry. A host restart recovers an interrupted command and keeps pending or offered inputs in order; a source whose last run produced events still runs again as soon as its remaining inputs are admitted. External commands must produce stable IDs so a repeated poll does not cause a second user turn.

`GET /api/agent/threads/:threadId/wake-sources` returns `sources`, `events` and `commandOutput: "ndjson"`. A command can check that field to discover that multi-line output is accepted before emitting more than one event.

## Authenticated event input

For an approved external producer on the same host, configure `WORKSTATION_WAKE_TOKEN` in the private Workstation service environment. POST only to loopback with `Authorization: Bearer <token>` and JSON `{ "sourceId": "source", "eventId": "stable-id", "message": "text" }` at `/api/agent/threads/:threadId/wake-events`. A `sourceId` naming a cancelled source of that thread returns `400` and nothing is retained, since its input would never be offered; saving the source again re-enables it. A 202 response confirms **durable custody, not native admission, model response, or outbound delivery**. The source-event pair is deduplicated per thread: a repeat returns the stored event and is never delivered again, even if the source now sends different wording for it. An unknown thread returns `404`; a thread that could not be read (for example a runtime timeout) returns `503`. A `503` from a failed state write means the input may be held only in memory: retry with the **same** pair; the retry is acknowledged only once the state is on disk, and nothing is offered to the thread until then. GET `/api/agent/threads/:threadId/wake-sources` and wait for the matching event's `status: "admitted"` before acknowledging upstream. Do not put secrets in messages or pass raw third-party content across a trusted-input boundary. This interface must remain on loopback or an authenticated private connection; it is not public ingress.

The producer-neutral mapping is: keep one durable `threadId`; give each upstream input one stable `sourceId`/`eventId` pair; persist or retry that *same* pair until its receipt is `admitted`. A timer, peer or other trusted adapter uses this same route, not a foreground model turn, another agent, or a separate queue consumer. The dispatcher serializes events on that thread, steers the existing active turn using its expected turn ID, and resumes/starts on that same thread when idle. An ambiguous native offer is **not** sent again merely because a connection timed out; it is offered again only on positive native proof that it did not land (see [Unconfirmed offers](#unconfirmed-offers)), or explicitly held under the documented operator procedure. Upstream provider delivery and agent completion require separate receipts. This is a local authenticated host contract, not permission to expose an arbitrary remote sender or provider body directly to the agent.

The interactive `/api/agent/chat/steer` path also accepts an optional bounded `clientUserMessageId`, passed unchanged to native `turn/steer` with the expected turn ID. That direct response only identifies a turn; unlike the wake-event route, it does **not** persist an event before admission or implement external-source retry/ordering. Use the durable event route for infrastructure input. Native command execution is distinct from steer: an agent's supported supervised/background command must retain its process/session ID and eventual output/exit, while another event steers the turn; do not restart or duplicate the command to accept a new input. A unit fixture exercises two inputs during an unfinished command, but installed long-command and post-restart native process acceptance remain separate release checks.

## Common native input path

Ordinary interactive streams, direct active-turn steers, and durable timer or
external inputs share Workstation's existing-thread resume policy and native
input submission in `CodexService`. A prepared new chat starts its first turn;
an existing idle chat resumes **that exact thread** before `turn/start`; an
active turn uses `turn/steer` with its expected turn ID. A failed resume does
not substitute a new conversation. Each producer retains its own authentication
and permissions: this common native path does not make an external sender a
desktop tool caller or grant access to a different thread. The interactive
`/api/agent/chat/stream` endpoint may accept a bounded
`clientUserMessageId` supplied by a caller that already persists that identity;
the durable wake route derives and stores one from its thread/source/event ID.
An RPC turn ID alone is not a durable input receipt. Inspect native history for
the exact client ID or marker before acknowledging an external source; an
ambiguous offered input stays in order until it is reconciled, proven absent
and offered again, or explicitly held under the operator no-replay procedure.
History is read in pages, newest first, back to the first turn whose recorded
end time is older than the oldest input of the thread still awaiting admission
(less one minute): a turn that ended before that input was created cannot hold
it. A turn with no recorded end time (running, or interrupted by a crash) may
have taken an input steered into it long after it started, so it is always
read and the scan continues past it. A scan that reaches its page bound fails
as an unreadable history; it never reports the rest as absent. An admitted
input is never inspected again. Existence and workspace checks on the input path read
the thread without its turns. Workstation does not
own native command processes: supported OIX process/session output and exit
continue while a new input is steered, and must not be restarted to accept it.

An operator can inspect native queue custody without starting another runtime: GET `/api/agent/threads/:threadId/native-custody` on loopback using the same bearer token. The existing app-server client reads `thread/read` and paginated `thread/queue/list` and returns only native status, active approval/user-input flags, last turn ID/status, bounded queued-submission IDs and client-message IDs, and count. No input bodies or transcript text are returned. It fails closed on invalid pagination, unavailable native queue support, malformed IDs, or authentication failure. The Workstation host's normal session access policy still applies. This endpoint is **diagnostic**, not an admission acknowledgement or a substitute for maintaining event custody.

For a host-wide pre-restart check, GET `/api/agent/custody/global` on loopback with that same bearer token. This read-only diagnostic counts **all** in-process Workstation message queues, pending agent-tab requests, pending tab startup inputs, created tab requests awaiting completion, and pending approvals without applying the current window/workspace filter. It returns opaque queue owner/request IDs, not queued text or approval details, and fails with 503 instead of an invented empty result when inspection fails. `nativeQueueScope: "thread-only"` explicitly means this endpoint does **not** attest a global native OIX queue: inspect every affected native thread with the separate route above and preserve any unknown custody as a stop condition. An empty per-thread renderer list is not a substitute for the global check. Neither endpoint freezes incoming producers; take a fresh snapshot after coordinating an input checkpoint and immediately before a supervised restart.

To locate the owner of **one already-pending** approval without changing it, GET `/api/agent/custody/approvals/:approvalId?threadId=:threadId` using that bearer token and loopback. An exact pending ID and matching captured owner thread are required; other threads yield 404, regardless of window. If the owner was captured as CLI with no thread binding, use `?cliUnbound=1` with that exact ID instead. A non-CLI unbound request cannot use that exception. The result contains only approval ID, pending status, registered tool name, and captured owner kind/thread/window session/workspace; never tool arguments, questions, provider data, or a disposition capability. Missing/resolved IDs return 404; invalid scope returns 400; unavailable inspection fails 503. The operator must still find the legitimate owner UI/session and obtain its normal approval—these metadata routes cannot approve or deny it.

The input begins with `[Wake event source/id]`. On restart, the dispatcher checks native history for this marker. If a submission remains ambiguous without a native receipt, it stays offered rather than risking a duplicate user turn; elapsed time alone does not prove rejection.

### Accepted and admitted

An input passes through three states on its way into a thread:

- **offered**: it is marked offered on disk, then the steer or start RPC is made. A crash or a lost response at this point leaves an offer of **unknown outcome**: the runtime may or may not have taken it.
- **accepted**: the RPC returned a turn ID and that ID is saved with the input (still `status: "offered"`, now with `turnId`). The runtime has taken the input, but a steered input reaches thread history only when the running turn consumes it, which may take seconds or minutes.
- **admitted**: its client ID or marker is in thread history. Only this is a receipt; the message body is erased from the state file only then.

Inputs of one thread are offered strictly one after another, in queue order, never concurrently. An accepted input does **not** hold back the next one, so a burst sent to a thread with a running turn is steered into that turn within one pass, each input exactly once. What holds back the later inputs of a thread (nothing after it is offered in that pass, although later inputs that were already offered are still checked for their receipts):

- an offer of unknown outcome;
- an accepted input whose turn is known to have ended without its receipt appearing (it may be offered again; see below);
- an input under review after the re-offer limit;
- a pending input in backoff after a failure (backoff only delays offering that input: a pending input that was offered before, and returned for a re-offer, is still checked for its receipt in every pass and admitted as soon as it appears; an offered or accepted input is never in backoff and is admitted as soon as its receipt appears);
- an input that has just returned to pending for a re-offer, until the next pass offers it;
- an operator decision in progress on an earlier input.

This applies to an offered input whatever its source, paused or not. Only **pending** inputs of a paused source are skipped without holding back others, as described under pause; pending inputs of a cancelled source are never offered and hold back nothing.

The steer target is the active turn in the thread's history. History may lag an RPC made moments earlier: when it shows no active turn but the thread has an accepted input, anywhere in its queue, whose turn is not known to have ended, the next input steers that turn (the most recently offered one) instead of starting another. A turn is known to have ended when a steer to it was refused as "no active turn" or native custody reported it terminal; such a refusal returns the input to pending, and a later pass starts the thread once the earlier inputs are settled. A turn is started only when there is no turn to steer and no offer of the thread, anywhere in its queue and from any source, has an unknown outcome, so two inputs never start two overlapping turns on one thread.

Each pass reads a thread's history once, back to its oldest input awaiting admission, and admits, in queue order, every input whose client ID or marker it shows. After a pass that itself changed state (offered, admitted, returned or settled an input) while accepted inputs still await their receipts, the dispatcher looks again within about a quarter second; a pass that changed nothing itself leaves them to the ordinary two-second interval, whatever other callers saved meanwhile, so waiting on a turn that has not yet consumed its input does not cause rapid passes.

A history read that fails or times out leaves the thread's inputs as they are for that pass. It is recorded, with its backoff, only on a pending input it kept from being offered (when that input was the first of the thread to need the read), never on an offered input; accepted inputs keep waiting without holding anything back and are admitted as soon as history can be read again. At most one history read per thread is outstanding: a read that timed out is not started again until it settles.

After a restart an accepted input is still `offered` with its `turnId` on disk. It is reconciled like any other: admitted when its receipt appears, never offered again without the proof below, and its body is kept until then. A crash (or a failed write) after the RPC returned but before its turn was saved leaves, on disk, an offer of unknown outcome, which holds back later inputs and prevents any start on the thread until its receipt appears or the proof below returns it to pending.

### Unconfirmed offers

An offered input that has no receipt is offered again automatically only on positive proof that it is not in the thread. This covers an offer whose RPC result was lost (a timeout, a disconnect, a crash) and an accepted steer whose turn ended without consuming it. The proof, for each such input on its own, within one pass: it was offered at least one minute ago; the pass's shared history read shows no active turn and no receipt; then a **fresh** history read, the native custody read and a second **fresh** history read are made, in that order, and both fresh reads show neither its client ID nor its marker and no active turn, while custody reports its turn ended (or, when no turn was recorded for the offer, the latest turn ended or there is none), the thread not active, and an empty native queue. A complete proof is only noted. The input is acted on only when a **later pass, at least 15 seconds after the first, observes the complete proof again**. Any contrary observation in between (a receipt, an active turn or thread, a queued submission, a turn that is not terminal, a failed read) discards the note, so the 15 seconds start again from the next complete proof; admission, hold, refusal and removal discard it too, as does an operator hold or reconcile of that input, whether or not it succeeds (a pass during one skips the input), and so does a restart, which keeps nothing of it. The second observation covers an accepted steer that the runtime carries over into its next turn: between turns it is in neither the queue, nor the ended turn, nor the briefly idle thread status, nor history, but by the later pass the next turn is active or holds its receipt.

It then returns to `pending` and is offered again with the **same** client ID and marker, so a late receipt of the first offer is still recognised. Nothing more is offered on the thread in that pass; in the next pass it is the first of the thread's pending inputs to be offered, ahead of every later pending input. Two exceptions: when its source is paused it waits, pending, like any input of a paused source, and the thread's other inputs proceed (a paused source can never hold a thread's other inputs back indefinitely); and when its source has been cancelled it is removed, like any input of a cancelled source that was not delivered. Later inputs that were already accepted or admitted stay as they are: in this rare case that one input reaches the thread after inputs that were sent after it, because those are already in the thread. A receipt observed at any point admits it instead. At most three such re-offers are made; after that, on the next such two-observation proof, it needs review and shows the error `Input could not be confirmed; operator review required`. A configured source's input stays `offered` (and keeps holding back that thread's later inputs) with its source in error; a thread input, which has no source to review, is set `held` with its text and ID retained, the caller's custody read and stream report `held`, and later inputs proceed. Without native custody inspection none of this happens and the input stays offered. It does not promise exactly-once tool side effects or message delivery. The provider-specific reply tool remains the way to answer; scheduling and input custody are not an outbound queue. The only automatic outbound paths are the outcome return for a sender-attributed programmatic task and the Goal notice to that thread's most recent sender, described below.

New wake submissions also carry a stable native `clientUserMessageId` derived from their thread/source/event identity. Either that ID on a persisted native user message or the exact text marker is an admission receipt; an accepted RPC, a completed turn, or a queue count alone is not. An offered input without either receipt is offered again only under the proof rule above, never on elapsed time. For a truly terminal, queue-empty ambiguous offer, the local operator can explicitly choose **not to replay** it: POST `/api/agent/threads/:threadId/wake-events/:sourceId/:eventId/hold` with the same loopback bearer authorization and `{ "turnId": "exact-offered-turn-id", "confirmedNoReplay": true }`. The server rechecks the exact offered event, terminal native turn, idle thread, empty native queue and absence of either receipt before preserving it as `held` (not admitted) and letting later inputs proceed. The held source remains in error for separate review; this operation never acknowledges the upstream provider, restarts the application, or resubmits the held text. If any check fails, stop and reconcile the native receipt rather than calling hold repeatedly. Do not use this endpoint to waive ordinary provider input or skip work without a documented operator decision.

Once admitted, the original message body and transient error are erased from the wake-source state; the compact `(thread, source, event ID)` receipt remains for durable deduplication and status queries. The 10,000-event guard applies only to inputs still awaiting admission, not lifetime admitted messages. Receipts intentionally remain until the thread's data is retired; the private state file grows with unique IDs and should be included in normal Workstation backups. Do not hand-edit it to clear a limit: removing IDs can cause old upstream redeliveries to appear as new input.

An operator-held event is likewise retained with its original text and ID for separate review, but it is **not** an admission or an upstream acknowledgement and cannot be automatically replayed. Its source remains in error; after resolving the missing work, the operator may explicitly re-save that source for future runs without erasing the held ID. Only pending/offered inputs count toward the awaiting-admission limit.

## Programmatic input to an existing thread

Every programmatic message addressed to an existing thread goes through the same per-thread queue as schedules, commands, channel input and the event route above. `POST /api/agent/tasks/stream` and `POST /api/agent/tasks` with a `threadId` do not run a turn of their own: they retain the message as a wake event of the fixed source `thread-input`, whose event ID is the request's `clientUserMessageId`, and return once it is on disk. The dispatcher then delivers it in order with the thread's other inputs, steering an active turn or starting the idle thread, one offer at a time and without waiting for earlier receipts (see [Accepted and admitted](#accepted-and-admitted)), and recovers it after a restart. A busy thread is not an error; the input simply waits its turn.

- `clientUserMessageId` is required (letters, digits, `_`, `-`, at most 160). A repeat of the same ID never submits again: it answers with the state of the stored input.
- `workspace` is required as for any headless task and must equal the thread's own workspace (read from the thread); otherwise 400.
- A repeat with the same ID and the same message and sender is answered from the stored input, before the thread is read or the workspace compared, so it is answered even while the runtime is unavailable; the same ID with a different message or sender returns `409 { error: "Client ID already used for different input." }`, likewise without reading the thread, and never reveals the stored input. (While a state write is outstanding, or after one failed, a repeat is not answered from memory; it goes through ingestion, which writes first.)
- An unknown thread returns 404; a thread that could not be read (for example a runtime timeout) returns 503 and nothing is retained. A 503 saying the input could not be saved means it may be held only in memory: retry with the same `clientUserMessageId`; the retry succeeds once the state is on disk.
- `model`, `reasoningEffort`, `modelConfig`, `runtimeConfig`, `system`, `timeoutMs` and `idleTimeoutMs` return 400: the thread keeps its own settings and an input has no time limit of its own.
- The message, including any sender line, may be at most 32,000 characters; a longer one returns 400.
- The source ID `thread-input` is reserved: the event route above and source configuration reject it.

`POST /api/agent/tasks` answers `202 { threadId, clientUserMessageId, status }` without waiting; for an input already refused (see below; a repeat of its ID), the body also carries `code` and `parentThreadId`. `POST /api/agent/tasks/stream` answers with Server-Sent Events: `submission` `{ threadId, clientUserMessageId, status }` as soon as the input is durable; `accepted` `{ threadId, turnId, clientUserMessageId }` as soon as the runtime has accepted it into that turn; then, once it is admitted (its receipt is in thread history), `thread`, `turn` `{ threadId, turnId }` (the turn holding the receipt; no status is claimed, since that turn may already have ended) and `admitted` `{ threadId, turnId, clientUserMessageId }`, and the stream ends; the turn continues on its own. `accepted` always comes before `admitted` when a turn is known, even when the receipt was observed before the acceptance could be reported. `accepted` is not a receipt: a steered input is admitted only when the running turn consumes it. The turn in `admitted` is the turn that holds the receipt, which may differ from the one in `accepted` if a later turn consumed the input. If the input is not admitted within 90 seconds, or the service stops meanwhile, the stream ends with `queued` `{ threadId, clientUserMessageId, status }` and no `error`: the input remains retained and is delivered in order. An input held under the unconfirmed-offer rule ends the stream with `held`. Closing the stream early, even before the `submission` event is written, changes nothing for the input, and the server stops observing it at once. Without a `threadId`, both routes create a new thread and run its first turn as before.

`GET /api/agent/threads/:threadId/submissions/:clientUserMessageId/custody` (loopback, with the bearer token described above) returns `{ threadId, clientUserMessageId, status }` with `status` one of `pending`, `offered`, `admitted`, `held` or `refused`, plus `turnId` when known, `accepted: true` for an offered input whose turn the runtime returned and is saved (accepted, receipt awaited; a turn not yet on disk is not reported, here or as the stream's `accepted`), `outcomeReturn: "turn_unknown"` for a sender-attributed input admitted without a known turn (no outcome is returned for it) and, for a refusal, `code` and `parentThreadId`. It never returns the message. An unknown ID is 404. The thread and client IDs use the same alphabet as the input request (letters, digits, `_`, `-`, at most 160); others are 400. The read requires `WORKSTATION_WAKE_TOKEN` to be configured: without it every request is 401, so the read is never open. These inputs also appear in the thread's `wake-sources` listing like any other event.

The core decides whether a thread spawned by another agent thread accepts direct input; the server does not refuse on its own reading of the thread. When the core refuses (on resume, turn start or steer), the input is settled as `refused`: it was never delivered, is not retried, and does not hold back later inputs. A waiting stream ends with an SSE `error` event carrying `code: "subagent_direct_input_unsupported"`, the `threadId` and its `parentThreadId` (`null` when the thread cannot be read), so the work can be sent to the parent thread instead; the custody read and a repeated request report the same. A configured source whose input is refused this way is put in error and stops until it is saved again; a restart does not re-arm it (unlike an ordinary transient command error, which recovers on a bounded timer after a restart).

## Work handed over by another agent host

Another agent host hands work to an existing thread with the input above and an optional `sender` object, `{ "computer": "peer-host", "thread": "origin-thread-id" }`. `computer` must match `^[a-z][a-z0-9-]{1,62}$`; the optional `thread` uses the client-ID alphabet. No other keys are accepted. A sender is only accepted together with `threadId`. Any invalid shape returns 400 before anything is retained. The sender is stored with the wake event (and kept after admission) and the thread receives exactly one header line before the unchanged message:

```text
[Sender: peer-host thread origin-thread-id]
Original message text
```

(`[Sender: peer-host]` when no thread was given.) A request without `sender` is submitted without a header and has no outcome returned.

### Outcome returns

When a sender-attributed input is admitted to a native turn, the server records that turn in a separate private file, `outcome-returns-2.json`, next to `wake-sources.json` (atomically replaced, mode 0600). Entries are `watching` until the core reports that turn ended, then `pending` with its outcome (`completed`, `failed` or `interrupted`) and the turn's final assistant message, truncated to 3,000 characters. On startup, each watched turn is checked against native thread history in case it ended while the server was down, a watch recorded later for a turn not seen ending is checked when it is recorded, and every turn still watched is checked again every minute, so a missed notification or a failed or timed-out read does not leave it watching until a restart; each read pages back newest first only as far as that turn (at most one read per turn at a time: a read is waited for at most 10 seconds, but no other read of that turn starts until it settles). The admitting turn is the turn holding the input's receipt: the turn it started, or the turn that consumed it when steered. When that turn cannot be identified, no watch is recorded and the input's custody read shows `outcomeReturn: "turn_unknown"`. Every sender-attributed input admitted to a turn is watched separately: when several senders' inputs started or steered the same turn, each gets its own return, with its own `id` and `clientUserMessageId`. The wake event is marked once its watch is on disk (a watch whose write failed is not kept, so a retry records it again); an admitted, sender-attributed event without that mark (the record failed or the store was full, or a restart fell in between) is handed over again every minute and at startup, so a watch is neither lost nor recorded twice.

Delivery uses a host command configured in the Workstation service environment: `WORKSTATION_OUTCOME_RETURN_COMMAND` holds a JSON array of strings (argv, executed without a shell). For each due pending entry, the command receives one JSON object on standard input:

```json
{"version":1,"kind":"turn","id":"<sha256 of threadId:turnId:clientUserMessageId>","to":{"computer":"peer-host","thread":"origin-thread-id"},"from":{"threadId":"...","turnId":"..."},"clientUserMessageId":"...","outcome":"completed","summary":"..."}
```

The same command also receives **Goal notices** (described below) with `"kind":"goal"`. Every payload has `version: 1`, `kind`, `id`, `to`, `from.threadId` and a plain-text `summary`; `outcome`, `from.turnId` and `clientUserMessageId` exist only for `kind: "turn"`. Payloads written by earlier versions had no `kind`; treat a missing `kind` as `"turn"`. A command must branch on `kind`, and for any kind it does not recognise it should deliver `summary` as a plain message to `to`, exactly as it delivers an outcome. It must not fail on an unknown kind or extra fields, since a failure is retried until the attempt limit.

A command that delivers an outcome or a Goal notice as a message to the sender's thread must submit it with a client message ID of the form `outcome-<id>`, for both kinds. A submission with that prefix is a delivery: it is never itself watched and never makes its sender the receiving thread's sender. Without this, two idle threads would return each other's outcome returns without end.

Exit 0 marks the entry `delivered` (its summary text is then dropped). Any other exit, a spawn failure, or the two-minute timeout counts an attempt and schedules the next one after 1, 2, 4, 8 and then every 15 minutes; after 40 attempts the entry stays visible as `failed`. Delivery is at least once: a restart while a command runs retries it, so the receiving side should deduplicate on `id`. Only add a command you trust.

If the variable is unset or not a non-empty JSON string array, nothing is spawned and entries simply remain `pending`; this is logged once at startup. `GET /api/agent/outcome-returns` lists entries with `id`, `threadId`, `turnId`, `sender`, `status`, `outcome`, `attempts`, `nextAttemptAt` and `updatedAt`, never the summary text; Goal notice entries instead have `kind: "goal"` and `goal` in place of `turnId` and `outcome`, and an unrouted Goal notice has `status: "unrouted"` and `unrouted` (its reason) in place of `sender`. The newest 500 entries are kept; delivered, failed or unrouted entries are dropped first, and a new watch or notice is refused (and logged) rather than dropping an undelivered one.

### Goal notices

A turn outcome does not tell the sender when the worker thread's [Goal](goals.md) later stops: the runtime can block it on a failed turn, a usage or budget limit can stop it, or the worker or an operator can pause or block it, long after the last attributed turn was returned. Workstation therefore also tells the Goal's **assigner** when its Goal settles in a new status:

- `paused`, `blocked`, `usageLimited` or `budgetLimited`: reported when the status differs from the last notice for that Goal.
- `complete`: reported once. A completed Goal is final, so a later Goal on the thread becoming active is not reported as "active again".
- `active`: reported only when the last notice for the thread was one of the stopped statuses above, so the sender's picture is corrected.

On its first start, a release with this format carries over the entries of the earlier `outcome-returns.json`, writes `outcome-returns-2.json` with them before anything else changes, and leaves the earlier file unchanged, so the release that wrote it can still read it.

A Goal is identified by its thread and its native `createdAt`. Its assigner is bound once, the first time the Goal is observed (a `thread/goal/updated` notification, or the startup read below), from the sender-attributed inputs recorded in `outcome-returns-2.json` for that thread, in this order:

1. If the notification names a turn and that turn's recorded inputs have exactly one distinct sender with a `thread`, that sender (source `turn`).
2. Otherwise, if the thread's recorded inputs have exactly one distinct sender with a `thread`, that sender (source `sole_sender`). This also binds Goals that existed before assigners were recorded.
3. Otherwise, if the thread has no recorded input at all, nothing is bound and nothing is ever sent or stored for the Goal.
4. Otherwise the Goal is recorded unrouted: `no_assigner` when no sender named a thread, `ambiguous_assigner` when several did.

The binding is kept in the same file (`goalAssigners`, the newest 500 Goals) and never changes afterwards, so a later sender to the thread, with or without a thread, does not receive the Goal's notices. An unrouted Goal's notices are recorded with `status: "unrouted"` and the reason, listed like other entries, never passed to the command, and logged as one line with the thread ID, the Goal status and the unrouted reason. Deliveries (`outcome-` client IDs) are never recorded as inputs. A cleared Goal is not reported.

A change must remain settled for 25 seconds; a Goal that flips between statuses within that time produces at most one notice for the state it settles in. A block caused by a temporary model-capacity refusal that the automatic resume (see [Goals](goals.md)) has scheduled is reported once, with reason `capacity_retry_pending`, however many attempts follow. Its outcome is reported too: an `active` notice when the resume works, or, if the resume does not reverse it or gives up after its two-hour window, a second `blocked` notice (reason `model_capacity_exhausted` when it gave up), even when the Goal's status and times have not changed since the first.

The payload carries no objective and no message text:

```json
{"version":1,"kind":"goal","id":"<sha256 of goal:threadId:createdAt:status:updatedAt>","to":{"computer":"peer-host","thread":"origin-thread-id"},"from":{"threadId":"..."},"goal":{"status":"blocked","previousStatus":"active","reason":"turn_error","createdAt":1763251200,"updatedAt":1763254800,"goalId":"…","missionRevision":2,"lifecycleRevision":5},"summary":"Goal on thread ... is blocked (status blocked, previously active; reason turn_error; goal …, mission revision 2, lifecycle revision 5)."}
```

`createdAt` and `updatedAt` are the native Goal's own times: `createdAt` identifies the Goal on the thread and `updatedAt` the change, so `id` is stable for one change and receivers deduplicate on it as for outcomes. The `capacity_retry_pending` notice appends `:capacity_retry_pending` to the hashed text, so the block's later outcome has its own `id`. `goalId`, `missionRevision` and `lifecycleRevision` are the native Goal identity and revisions read when the notice is recorded; they are present only when the runtime reports them for the same Goal in the same status, and are omitted otherwise. `previousStatus` is the status observed just before the change and is omitted when unknown (for example after a restart). `reason` is one of:

| Reason | Meaning |
| --- | --- |
| `turn_error` | The runtime blocked the Goal because the turn that ran it failed. |
| `capacity_retry_pending` | Transient: blocked by a model-capacity refusal and the automatic resume is pending. The outcome follows in a later notice. |
| `model_capacity_exhausted` | As above for a model-capacity refusal, after the automatic resume gave up. |
| `usage_limit` | An account or provider usage limit stopped the Goal. |
| `budget_limit` | The Goal's explicit budget was reached. |
| `changed_during_turn` | Changed during a turn that did not fail: usually the agent's own Goal update, but also a runtime stop after repeated empty responses. The two are not distinguishable from the notification. |
| `changed_outside_turn` | Changed through the Goal API with no turn: a person, an app control, a peer, or the automatic resume. |
| `unknown` | Found at startup; the change happened while the server was not observing it. |

Notices use the same store, retry schedule, attempt limit and at-least-once delivery as outcomes. At startup, the 50 threads with the most recently attributed turns are each read once (one native Goal read per thread, bounded to 5 seconds) and a notice is queued (or recorded unrouted) for any Goal whose current status is due by the rules above, for example one that stopped while the server was down. Nothing is read when no thread has a recorded sender. If a thread's last notice was dropped by the 500-entry limit, a later startup can report its current state again; receivers deduplicate on `id`.

## Headless operation

Persist the thread ID on disk and resume that exact native thread after service restart. A missing thread must be repaired explicitly rather than silently replaced. Configure a command source through the same per-thread endpoint or through the Automations editor; do not run a second foreground polling consumer. Use an absolute executable with stable event IDs, and keep source-specific authentication in the provider's private configuration. There is no requirement to keep a Goal or turn running just to receive future input.

On an idle existing native thread, the wake path retains its original shell
environment and caller scope; it does not mint or install a new shell caller
when resuming a loaded thread. The existing Linux caller binding can recover
its authorization by the token already held in that thread's shell, without
persisting the token itself. A failed or ambiguous native start remains an
offered event for receipt inspection; it is offered again only under the
unconfirmed-offer proof rule, never on elapsed time. A source-only
fix does not resolve a previously offered event or prove that a running host
has been updated.

If an older saved thread has **no** usable CLI carrier, an authenticated
loopback operator may cold-bind the existing thread with
`POST /api/agent/threads/:threadId/caller/cold-bind` and JSON
`{"workspace":"/absolute/original/workspace"}` using the already-configured
`WORKSTATION_WAKE_TOKEN`. This submits no user input. It rejects a loaded or
active thread, any native/app queued input, pending approval or tab request,
pending/offered wake event, workspace mismatch, or a previously restricted
tool caller. The server rechecks native custody before resuming and leaves the
existing model/provider settings unchanged. Do not use it to mutate a loaded
thread's shell environment or to dispose held events. A successful response
is **not** proof of model output or that the CLI tool catalog is available in
the next actual turn: inspect `interpreter-app` from that original caller and
then verify a separate new event/turn receipt. An ambiguous response requires
fresh read-only custody, not a blind second bind or input replay.

To temporarily stop new work from one configured source without deleting its record or pending events, POST on loopback to `/api/agent/threads/:threadId/wake-sources/:sourceId/pause`; POST to the corresponding `/resume` path when ready. These local same-origin mutations preserve the source's configuration, next time and sequence, and any pending/offered event. While paused, the dispatcher neither launches a new command nor offers that source's event to native admission; an input it had already offered is still admitted when its receipt appears, since that is an observation, not an offer. Its pending inputs wait in place; inputs of other sources and thread inputs on the same thread proceed in their own order and are not held behind them, so after resuming a paused source's input may follow inputs that arrived later. An input of the paused source that is already **offered** holds back the thread exactly like any other offered input (an offer of unknown outcome also prevents any new turn from being started on the thread); if the unconfirmed-offer proof returns it to pending while the source is paused, it then waits like the source's other pending inputs, and the thread's other inputs proceed. A command already running is **not killed**: pause waits for its output and durable event/error to settle, and waits for the preceding native-offer tick. A successful pause response includes `source` and a bounded `drain` object with `drained: true`, false command/offer in-flight flags, and that source's pending/offered event counts. A drain error leaves the source paused but is **not** a safe stop receipt. This source-specific response is not a global queue, native-turn, or external-provider lease: before stopping a service, separately inspect all sources, native offers/queues, active turns, approvals, and supervised work, then keep exact rollback custody. Pausing does not inspect, freeze or acknowledge an external provider queue, and a provider poll may have made an upstream message temporarily invisible. Do not use DELETE/PUT as a pause/restart substitute: DELETE cancels and discards pending input; PUT edits and resets timing. A paused source must be resumed before it can be edited. As with ordinary admission, verify the event's durable native `admitted` receipt before upstream acknowledgement.
